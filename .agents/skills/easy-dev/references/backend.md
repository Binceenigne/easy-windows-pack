# 后端与平台边界

触发：API、Python 服务、数据持久化、后台任务或 JS ↔ Python 桥接。

## 先查能力，再添入口

查看项目 `index.md` 的服务/桥接清单，再读相似处理器、输入模型和调用方。可复用现有用例、错误类型与数据访问时不要另造一套业务规则。界面换一种表现不等于后端需要新增一套接口。

处理器负责输入边界、调用和响应；核心规则应能脱离具体界面被调用。IO、事务和平台调用放在可定位的模块中。小功能可用明确命名的函数与现有数据模型，不强制每个接口都建立 repository/service/DTO 三件套。

## 正确性底线不降级

在可信服务端或宿主验证权限、输入和敏感操作；前端禁用按钮不能代替权限检查。不要暴露任意命令执行、任意文件读取或全部 Python 对象供 UI 直接调用。沿用白名单和现有授权机制。

保持现有输入输出契约、错误码和版本兼容。超时、取消、重试和幂等按操作风险处理；创建订单、安装更新等有副作用操作不能因为请求失败就盲目重试。日志不泄露令牌或隐私信息。

涉及数据库写入时明确事务边界；涉及异步任务时明确状态所有权、异常归属、取消与资源释放。避免在事件/UI 线程等待耗时 IO，也不要为了“异步”把线程不安全的对象并发调用。

## 依赖与验证

领域规则优先用简单数据及可替换依赖表达；仅在隔离易变平台或测试边界确有收益时新增抽象接口。模块的拆分依据职责和变化原因，而不是文件长度。

修改公共契约需覆盖至少有代表性的调用链及相关失败情形；权限、数据破坏、并发等高风险不能以“省时间”为由免检。可沿用宿主测试，无需为了普通接口引入新测试框架。

新增/移动服务、改变公开用途或调用方式时同步 `index.md`。纯后端修复不改 `design.md`；影响用户交互契约时才更新相应描述。
