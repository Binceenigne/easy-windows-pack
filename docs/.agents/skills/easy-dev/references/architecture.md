# 模块架构

触发：新业务模块、跨层功能、目录与依赖调整。仅改一个文案或颜色时不需要本分片。

## 先适应，再改善

看邻近目录、项目清单与入口文件，延续已有的健康组织方式。文件夹名称没有强制标准；目标是读目录就能找到职责，修改一处不会牵动无关业务。

优先业务内聚：同一功能的页面、局部组件、状态与访问逻辑放近；跨功能确有复用价值的实现再进入共享区。不要将所有东西堆进 `common`、`utils` 或一个巨大的 `service`。

## 边界比层数重要

- 展示层组织交互与视图；应用逻辑处理用例；数据/平台访问放在明确的适配边界。
- 共享 UI 不认识具体页面、业务 store 或宿主数据库。不同功能不越过公开入口去访问彼此的私有文件。
- 复杂、稳定的业务规则尽量不依赖 HTTP、ORM 或 Win32 类型。小型直接 CRUD 不必先制造完整领域层、仓储接口与工厂体系。
- 依赖注入可用构造参数、普通函数或现有容器。只有需要替换、隔离副作用或清晰表达边界时才新增接口。
- 尽量避免循环引用。公共导出入口可以存在，不照搬“禁止所有 index/barrel”之类与宿主不符的限制。

## 可选形态，不是迁移命令

```text
frontend/src/
  app/                    # 启动、路由、全局装配
  features/<feature>/     # 页面、业务组件、composables、访问逻辑
  shared/ui/              # 跨功能基础组件
  shared/styles/          # token 与共享样式
backend/
  features/<feature>/     # handler、用例、必要的数据访问
  infrastructure/         # 数据库、网络、平台实现
```

原生小项目可以只有 `frontend/components/`、`frontend/styles/` 和若干 Python 模块。仅当职责已混杂、独立变化或产生真实重复时拆分；不设置必须多少文件、多少行或多少层的指标。

## 修改时保护契约

重命名文件后更新真实调用方，但路由、持久化键、事件名、CSS 公共变量、桥接方法等外部契约不能当作普通局部符号随意改名。需要改变时说明兼容方式；不顺手做全仓迁移。

结构/入口改变，同步项目 `index.md`；只在影响全局产品约定时改 `design.md`。架构取舍有实际后果时留一句缘由，普通拆分无需额外设计报告。
